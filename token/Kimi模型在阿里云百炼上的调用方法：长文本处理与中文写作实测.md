## 二、API 调用方法详解

百炼平台支持通过 HTTP API 和 Python SDK 两种方式调用 Kimi 模型，以下分别介绍。

### 2.1 HTTP API 直接调用

```bash
curl https://dashscope.aliyuncs.com/api/v1/services/aigc/text-generation/generation \
  -H "Authorization: Bearer $DASHSCOPE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "kimi-long",
    "input": {
      "messages": [
        {"role": "system", "content": "你是一位专业的中文写作助手，擅长撰写深度文章。"},
        {"role": "user", "content": "请阅读以下长篇小说片段，并续写下一章：\n\n[此处插入长文本]"}
      ]
    },
    "parameters": {
      "result_format": "message",
      "max_tokens": 4096,
      "temperature": 0.7,
      "top_p": 0.9
    }
  }'
```

**关键参数说明：**

- `model`：指定模型版本，长文本任务务必选择支持超长上下文的型号。
- `messages`：对话历史数组，`system` 角色用于设定全局行为，`user` 角色传入用户请求。
- `max_tokens`：控制生成内容的最大长度，长文本续写建议设置为 2048–4096。
- `temperature`：控制生成随机性，中文写作建议 0.6–0.8，兼顾创意与连贯性。

### 2.2 Python SDK 调用

```python
from http import HTTPStatus
import dashscope

dashscope.api_key = "your-dashscope-api-key"

def call_kimi(prompt, system_prompt="你是一位专业的中文写作助手。"):
    messages = [
        {"role": "system", "content": system_prompt},
        {"role": "user", "content": prompt}
    ]

    response = dashscope.Generation.call(
        model="kimi-long",
        messages=messages,
        result_format="message",
        max_tokens=4096,
        temperature=0.7,
        top_p=0.9
    )

    if response.status_code == HTTPStatus.OK:
        return response.output.choices[0].message.content
    else:
        raise Exception(f"调用失败: {response.code} - {response.message}")

# 示例：长文本处理
long_document = open("novel_chapter.txt", "r", encoding="utf-8").read()
result = call_kimi(
    prompt=f"请阅读以下小说章节，分析人物关系并续写下一段：\n\n{long_document}"
)
print(result)
```

SDK 的优势在于自动处理重试、流式输出（Streaming）和错误封装。对于生产环境，建议开启流式响应以降低首 token 延迟：

```python
response = dashscope.Generation.call(
    model="kimi-long",
    messages=messages,
    result_format="message",
    stream=True,  # 开启流式输出
    ...
)

for chunk in response:
    if chunk.status_code == HTTPStatus.OK:
        print(chunk.output.choices[0].message.content, end="")
```

## 三、长文本处理实测

### 3.1 测试设计

为验证 Kimi 在长文本场景下的真实能力，我们设计了以下测试方案：

| 测试项 | 文本长度 | 任务类型 |
| --- | --- | --- |
| 学术论文摘要 | 15,000 字 | 提取核心观点、生成摘要 |
| 法律合同审查 | 30,000 字 | 识别风险条款、输出审查意见 |
| 长篇小说续写 | 80,000 字 | 保持人物设定与文风续写 |

所有测试均使用百炼平台上的 Kimi 长文本版（200K 上下文），通过上述 Python SDK 调用。

### 3.2 测试结果

**测试一：学术论文摘要**

输入一篇约 15,000 字的计算机视觉领域论文全文，要求生成 500 字中文摘要并列出创新点。

- **响应时间**：约 8 秒（含网络延迟）
- **摘要质量**：准确提炼了研究问题、方法、实验结果三要素，创新点归纳与原文高度一致。
- **关键发现**：模型能够识别论文中的数学公式和实验数据表格，并在摘要中正确引用相关数值。

**测试二：法律合同审查**

输入一份 30,000 字的股权投资协议，要求识别对投资方不利的条款。

- **响应时间**：约 15 秒
- **审查结果**：成功定位出 7 处潜在风险点，包括回购触发条件模糊、优先清算权范围过宽等。
- **上下文保持**：在输出审查意见时，能够准确引用原文条款编号，未出现「幻觉」或张冠李戴现象。

**测试三：长篇小说续写**

输入一部网络小说的前 80,000 字（约 20 章），要求续写第 21 章，保持原有文风与人物设定。

- **响应时间**：约 25 秒（生成 3000 字）
- **文风一致性**：续写段落延续了原文的古风叙事节奏，主要人物的语言风格（如主角的冷峻、配角的诙谐）保持连贯。
- **情节连贯性**：正确承接了上一章的悬念伏笔，未出现人设崩塌或时间线错乱。

## 四、中文写作实测

### 4.1 测试场景

除长文本理解外，Kimi 在中文原生写作任务中的表现同样关键。我们选取了四类典型场景进行测试：

1. **公文写作**：生成一份 2000 字的项目结题报告
2. **营销文案**：为一款智能家居产品撰写 10 条不同风格的 Slogan
3. **创意故事**：基于关键词「时间旅行、老北京茶馆、误会」创作短篇故事
4. **技术博客**：将一段 Python 代码的技术原理转化为通俗中文讲解

### 4.2 实测表现

**公文写作**

Prompt：

> 请撰写一份关于「基于大模型的智能客服系统研发」的项目结题报告，要求包含项目背景、技术路线、成果指标、经费使用情况、后续计划五个部分，语言正式、结构清晰。

Kimi 输出了一份格式规范的结题报告，各章节逻辑递进合理。特别值得肯定的是，模型自动生成了符合中文公文习惯的层级标题（一、（一）、1.），并在「成果指标」部分列出了可量化的数据（如「客服响应时间缩短 40%」），体现了对公文写作范式的理解。

**营销文案**

Prompt：

> 为一款「AI 语音助手音箱」撰写 10 条 Slogan，风格分别覆盖：科技感、温情路线、极简主义、年轻化、商务精英。

10 条 Slogan 风格区分度明显，且均符合中文语感。例如温情路线的「它记得你爱听的每一首歌，就像记得你回家的每一个夜晚」——对仗工整、意象贴切，无明显机翻痕迹。

**创意故事**

Prompt：

> 以「时间旅行、老北京茶馆、误会」为关键词，创作一篇 1500 字的短篇故事，要求情节有反转，语言带有京味儿。

生成的故事结构完整：现代程序员穿越到 1920 年北京茶馆，因方言差异引发一系列误会，最终发现茶馆老板竟是自己的曾祖父。语言上使用了「您嘞」「得嘞」「甭提」等京味儿词汇，人物对话鲜活。反转设计虽不算惊艳，但在 1500 字篇幅内做到了自圆其说。

**技术博客**

Prompt：

> 将以下 Python 装饰器代码的技术原理，用通俗易懂的中文写成一篇技术博客，面向有基础编程经验的读者：[代码片段]

Kimi 将装饰器的执行机制比喻为「给函数穿外套」，用「先穿内衣再穿外套，脱的时候先脱外套」来类比嵌套装饰器的执行顺序，比喻贴切且符合中文表达习惯。

## 五、成本与性能权衡

在百炼平台上调用 Kimi 模型，计费通常基于输入与输出的 token 总量。以长文本场景为例：

| 场景  | 输入 token | 输出 token | 预估成本（参考） |
| --- | --- | --- | --- |
| 论文摘要 | ~12K | ~1K | 低   |
| 合同审查 | ~25K | ~2K | 中   |
| 小说续写 | ~60K | ~4K | 中高  |

**优化建议：**

1. **Prompt 压缩**：对于超长的背景文档，可先在本地提取关键段落，减少输入 token 量。
2. **分段处理**：若任务允许，将 200K 文本拆分为 2–3 个 100K 的独立任务并行调用，可降低单次失败的重试成本。
3. **缓存复用**：对于多轮对话中的系统提示（System Prompt）和固定背景知识，利用百炼的 Prompt 缓存功能避免重复计费。
